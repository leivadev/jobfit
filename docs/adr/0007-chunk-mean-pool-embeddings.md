# Chunk + mean-pool embeddings, not truncation

`all-MiniLM-L6-v2` has a fixed 256-token input limit, but real `Long Description` text runs up to ~12,500 characters (median ~1,600) — far past what the model accepts in one pass. The obvious default is to let `sentence-transformers` silently truncate at encode time, keeping only the first ~256 tokens (title + opening of the description) and discarding the rest. We rejected silent truncation: it throws away most of most Jobs' content, and a future reader profiling recall problems would have no reason to suspect the encoder never saw most of the text. Instead, the Bi-encoder splits text into non-overlapping ~256-token chunks (via the model's own tokenizer), embeds each chunk, and mean-pools the raw chunk vectors into one final embedding — normalization still happens once, downstream, in FAISS index construction. This must apply symmetrically to Candidate Profile embedding at query time (not yet built — API-contract phase), since comparing a chunk-pooled Job vector against a truncated Candidate Profile vector would silently break the cosine-similarity assumption the whole design relies on. Revisit if evaluation (`docs/design/evaluation.md`) shows chunk-boundary splitting hurts ranking quality enough to justify overlap, or if a longer-context model replaces `all-MiniLM-L6-v2` outright.
